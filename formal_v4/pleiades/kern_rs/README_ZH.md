# Rust 版内核（kern_rs）

这是智能体天区搜索内核 `agent/kern.c` 的 Rust 移植版，2026-10-13 赛后完成。

**决赛提交的 c48 用的是 C 内核。** 本目录不改动 `agent/`，`agent/` 仍与提交的 ZIP 逐字节一致。

## 内核做什么

内核接收候选的视场中心和目标池，做三件事：
- 按官方光纤几何（`challenge/v4_fiber_map.py`：中心处的切平面，行沿高度、列沿方位）把目标分进光纤格子，每个格子取价值最高的目标；
- 对 20 档曝光时长和 3 种观测程序算出收益速率，选出最好的组合；
- 给选中的中心分配光纤，并为指向偏差拟合计算每个偏差假设的命中一致数。

智能体每一步都要对上千个候选中心调用它（1200 个锚点加细化），所以这是最热的一段计算。

## 和 C 版的关系

- **接口相同。** 导出同样的四个 C ABI 函数：`eval_centers`、`assign_center`、`offset_consistency`、`eval_groups`，签名也相同。编译产物叫 `libkern.so`，智能体的加载器（`agent/policy.py` 的 `Kernel`）先找 `libkern_linux_x86_64.so`，找不到再找 `libkern.so`，所以去掉 C 库、放进这个库就能直接替换。
- **结果逐位相同。** 每一步浮点运算的顺序都与 C 源码一致；三角函数用同一个 glibc libm（两边都调用 `sincos`、`sin`、`asin`）；两边都按 x86-64 基线编译，不生成 FMA 指令。
- **安全性。** 输入按长度转成切片，越界会立即终止（`panic = "abort"`），不会悄悄写坏内存。

## 构建

```bash
cd formal_v4/pleiades/kern_rs
cargo build --release          # 产物 target/release/libkern.so
```

需要 glibc 2.33 及以上（评测镜像 Debian bookworm 是 2.36）。C 版只需要 glibc 2.2.5 和 2.3.4。

## 验证

**函数级：`test_equiv.py`**
- 用随机输入同时调用两个库，逐位比较全部输出，浮点数按原始比特比较。
- 随机输入覆盖这些情况：
  - 光纤边长 1 到 12、格距 0.05 到 0.6 度；
  - 目标池 0 到 2500 个，包括视场外和远处的目标；
  - 价值表带 0、-inf 和大量完全相等的值，用来检查并列时的取舍；
  - 中心接近天顶、方位跨过 0 度；
  - 分组搜索用和不用高度带索引两种方式。
- 两个随机种子共跑 13000 组：

  | 种子 | 调用次数 | 候选中心 | 光纤格子 | 不一致 |
  |---|---:|---:|---:|---:|
  | 20261013（3000 组） | 17201 | 96887 | 222748 | 0 |
  | 777（10000 组） | 57845 | 324307 | 776197 | 0 |

**智能体级：`test_agent_equiv.sh`**
- 用最终版本 c48 在本地模拟卡上各跑前 N 步决策：一次用 C 内核，一次把 Rust 内核换进去，比较每一步的动作。
- 工具是 `lab/tools/eqtest.py`，它在进程内运行官方 v4 引擎，CPU 计费乘 0.01，预算很宽。多数卡上预算卡不住搜索规模，动作只取决于内核结果；HH1 例外，见下。
- 运行时不设模型 key，读日志和赛季策略都走规则兜底。

结果（每张卡前 1000 步）：

| 卡 | 说明 | 动作 | 整个智能体的 CPU（C → Rust） |
|---|---|---|---|
| HE1 | 隐藏卡模拟，E 类 | 完全相同 | 148 → 135 秒 |
| HF1 | 隐藏卡模拟，F 类 | 完全相同 | 165 → 159 秒 |
| HG1 | 隐藏卡模拟，G 类 | 完全相同 | 155 → 146 秒 |
| HH1 | 隐藏卡模拟，H 类（南极） | 第 45 步起不同，原因见下 | 251 → 231 秒 |
| FA2 | 正式 A 卡的近似 | 完全相同 | 193 → 174 秒 |
| FM1 | 多故障 | 完全相同 | 168 → 172 秒 |

HH1 上动作不同，原因不是内核结果不同，而是速度：
- 每一步搜多少个锚点，由这一步的预算和实测的每个锚点耗时决定（`agent/policy.py`：`afford = (0.85 × per_dec − fixed) / per_a`）。
- HH1 计算量大。从第 32 步起，锚点数被预算卡在 720 到 780 个左右，到不了上限 1200。
- Rust 内核实测每个锚点耗时更短，同样的预算下每步多搜 8 到 16 个锚点（第 32 步：735 对 719）。搜索范围不同，选出的指向随之略有不同（第 45 步：73.0752° 对 73.0784°）。
- 对照：同一个 C 内核跑两次，HH1 前 70 步的动作完全相同。

**影子对比：`test_agent_shadow.py`**
- 让智能体照常用 C 内核运行，同时把每一次内核调用原样交给 Rust 版再算一遍，用单独的输出缓冲区，逐位比较。
- 这直接检验智能体真实产生的输入，不受计时影响。

结果（每张卡前 1000 步，CPU 计费乘 0.01）：

| 卡 | `assign_center` | `offset_consistency` | `eval_groups` | 不一致 |
|---|---:|---:|---:|---:|
| HE1 | 917 | 916 | 7985 | 0 |
| HH1 | 921 | 26 | 7853 | 0 |

- HH1 上换成 Rust 内核后动作会变，但在同一批真实输入上两边结果逐位相同，所以动作变化来自计时，不来自内核。
- c48 的搜索走按中心分组的 `eval_groups`，这两次运行没有调用 `eval_centers`；它由函数级测试覆盖。
- 指向偏差已经确定、且这一步光纤全部命中时，智能体会跳过偏差拟合，所以 HH1 上 `offset_consistency` 调用少。

## 速度

同一台机器（EPYC 7F72），取 5 到 7 次中的最好成绩：

| 用例 | C | Rust |
|---|---:|---:|
| `eval_groups`：400 个中心，2 万个目标，10×10 光纤 | 88 ms | 43 ms |
| `eval_centers`：目标多数在视场外 | 16.4 ms | 9.3 ms |
| `eval_centers`：目标全在视场内 | 56.6 ms | 26.3 ms |
| `eval_centers`：3×3 光纤 | 24.5 ms | 18.1 ms |

Rust 版快，主要有三个原因：
1. 每个格子取最大值写成无分支的选择，编译成 `maxsd`。C 版的 `if (x > *cv) *cv = x;` 编译成条件跳转，随机数据下分支预测常常失败。
2. 三维向量用定长数组传递，去掉了逐元素的越界检查。
3. 格子下标的取整直接内联，不再调用库里的 `floor` 函数。

这些改写不改变任何运算结果。C 版做同样的改写应该也能快起来，但 `agent/` 要与提交的版本保持一致，所以没有改。
