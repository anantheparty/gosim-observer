# Pleiades 队 v4 观测智能体（线上赛最终版本）

本目录是 Pleiades 队在 GOSIM 2026 Agentic Observer（协议 v4）线上赛使用的智能体与实验框架。

- 执行层是传统算法：贝叶斯滤波，加上贪心速率最大化的天区搜索和 C 内核。
- 从 c18 起，在执行层之上加了大模型战略层（DeepSeek，见 2b 节）：开局分析任务卡并选择赛季策略，每周根据预报复审。
- 从 c21 起，我们扮演出题方做了对抗自检（见 2c 节），修掉了几处只对 A–D 成立的写死假设。
- c22–c25 做了第二轮对抗自检，包括极端组合卡和"历史天文事件"彩蛋卡（见 2d 节）。其中修掉了一个致命问题：1970 年以前的赛季会完全不观测。
- c27 针对新增正式赛卡 A1–D1 暴露的实际时间上限问题，加了引擎感知的时间规划（见 2e 节）。

- `agent/`：建议的最终版本 c27b 的完整源码，与平台上提交的 ZIP 逐字节一致（`agent.sha256`）。
- `lab/`：本地评测 harness、作业队列、世界生成器、打包与 docker 测试脚本、分析工具、隐藏卡模拟世界的规格。
- `sync_from_work.sh`：从开发机工作目录（`/home/shu/kamico/observer/work`）同步上面两部分。
  运行输出、生成的世界数据（约 250 MB）、线上下载结果和任何凭据都不进入仓库。

## 2. 算法概要

入口 `agent.py`：逐行 JSON 协议。初始化异常时用安全参数重试；单步决策异常时回复 `wait`，任何情况下都不破坏协议。

`policy.py` 的主要部分：

1. **天气与仪器信念（`Belief`）**：对 log 站点质量建模为季节均值 + 站点偏置 + 夜级 AR(1) + 时隙级 AR(1) + 公告天气事件偏移，
   每个仪器故障假设一个卡尔曼滤波器。故障起点先验采用生成器的时序（第 k 个故障位于 k·N/(c+1) ± 200 时隙），
   并维护故障个数 c 的后验（出现指向偏差或数据丢失等压力迹象时切换到多故障先验）。
   另外建模地震衰减，以及曝光开头、结尾或中间的未公告关闭时段，避免误报。
2. **故障报告**：前两次误报免费；根据后验和连续证据决定免费或付费报告，每次误报后提高证据门槛（`rep_esc`），
   付费次数上限之后仍保留强证据报告（`rep_override`）。
3. **指向偏差标定**：根据命中和落空在 (alt, az) 网格上计算似然；未见落空时把单元边界余量缩到 0.003 个 pitch。
4. **价值模型**：每个候选目标、每个曝光时长（20 档，60–3600 秒）、每个程序（DARK/BRIGHT/BACKUP）的期望得分提升。
   - 完成度：flux × 预测质量（天气 × 月光 × 大气质量），在曝光期间按梯形积分。
   - 部分完成折扣：(g/g_max)^γ，时间充裕时 γ 更大。
   - 时机因子：(当前高度因子 / 剩余季节最佳)^α。
   - 紧迫度：(S_ref/S)^0.5，S 为剩余的高仰角小时数。
   - 必选目标奖励：完成概率 × 50 × min(1, 15 / 足够好的剩余小时数)。
   - 观测请求奖励：按剩余目标分摊，时间充裕时放大。
5. **天区搜索**：
   - 按单目标价值速率选出 420 个互相分离的锚点。
   - C 内核 `eval_groups` 对每个候选中心做光纤单元分类，每个单元取最优目标，再按速率 value/(T+t0) 选曝光时长和程序。
   - 对前 20 个中心做 20 轮模式搜索细化，最后用 `assign_center` 分配光纤。
   - 候选池最多 40000 个目标。
6. **时间充裕模式**：容量比低时（如 D 卡），引入虚拟开销 t0（最大 2400 秒）、更强的部分完成折扣，并放大观测请求的权重。
7. **预算控制**：
   - 计费：按规则建议，每步成本取 min(CPU, 墙钟) / speed_factor，再用 `elapsed_seconds` 自校准计费比例。
   - 每步预算 = 剩余预算 / 预计剩余决策数；赛季早期可适度加速（仅在不超过线性进度时）。
   - 根据实测锚点成本回归出负担得起的搜索规模；候选池可自适应缩小，但有下限。
   - 剩余预算不足 3% 时进入紧急模式。
   - 墙钟保护：预算上限再取 (实际时间剩余 − 外推的引擎时间 − 5%) / speed_factor。前 5% 赛季不外推（c17w5 修复的就是这一点）。

## 2b. 大模型战略层（c18 起，`llm_strategist.py`）

评奖要求至少两个环节由大模型驱动（规则 §3.6）。c18 在不改动数值优化器的前提下，加了一个大模型战略层，分工如下：

| 环节 | 时机 | 大模型做什么 | 结果怎么用 |
|---|---|---|---|
| 数据解析 / 自然语言理解 | 开局 1 次 | 读任务卡：站点和仪器的自由文本说明、计分规则，以及智能体算好的星表、可见性、容量统计（需求/供给比、必选目标可完成小时数） | 生成结构化任务画像（容量受限、均衡或时间充裕；主要风险），作为后续规划的上下文 |
| 任务规划 | 开局 | 根据画像选择必选目标的赛季策略：`seasonal`（按含月光、季节、天气离散度的可完成小时数排紧迫度）或 `standard`（按高仰角小时数） | 设置优化器参数 `req_moon` / `req_moon_urg` |
| 计划自适应 | 每周预报到达时 | 结合未来 7 晚的预报、月相，以及进度（剩余和危险的必选目标、请求、故障、预算）复审策略 | 保持或切换策略 |

每一步的指向、光纤分配、曝光时长和程序仍由数值优化器决定；大模型决定它遵循的赛季策略。

两种策略都经过模拟验证：
- c17w6（seasonal）对 c17w5（standard）在 38 个世界上平均 +23（26/38 上升）。
- 在极端超载卡上（需求为可用时间的 11 倍），seasonal 会少完成必选目标（−900）。

这条经验写在给模型的策略说明里，规则回退也照此执行（需求/供给 > 5 时用 standard）。

**安全设计**
- 调用在后台线程异步进行，决策从不等待模型。
- 回答经白名单校验。
- 每次尝试 30 秒超时，每个问题最长 75 秒，429/5xx 按退避加抖动重试，每局最多 64 次。
- 离实际时间上限不足 5 分钟时不再调用。
- 没有 key、`OBSERVER_MODEL_DISABLED=1` 或服务不可用时，退回规则默认策略。
  实测在 key 无效、服务不可达、模型关闭、没有 key 四种情况下，运行都正常完成，墙钟不变。

**配置**：平台队伍变量 `OPENAI_API_KEY`（机密）、`OPENAI_BASE_URL=https://api.deepseek.com`、`OPENAI_MODEL=deepseek-flash`。
平台的 `evaluate` 默认"不提供模型"，评测 c18 时要用 `submit_tool.py evaluate --with-model`；隐藏决赛总会下发模型变量。

## 2c. 对抗自检（c21 起）

主办方可能有意让隐藏卡和 A–D 不同。引擎和协议是公开且固定的：事件种类、光纤几何约定、计分公式都写死在代码里，自由文本（仪器布局说明、请求的 `reason`）不参与计分。所以"不同"只能体现为合法范围内的参数。我们扮演出题方，用官方生成器构造了 27 张参数极端但合法的卡，每张都配一张只差这一处的对照卡：
`lab/gen_event.py` 改事件组合，`lab/mkred.py` 改计分、仪器和场景配置。

| 场景 | 改动 | c18 | c21 |
|---|---|---:|---:|
| 指向偏差 | 0.46°（官方参考上限 0.115°） | 13853 / 19606 | 26663 / 29110 |
| 仪器故障 | 5 次（原假设最多 4 次） | 24697 / 26477 | 25969 / 27578 |
| 故障 + 偏差 | 5 次故障 + 0.2° 偏差（B 类） | 40438 | 47097 |
| 误报罚分 | −1000、无免费次数 | 25895 | 26934 |

找到并修复的写死假设（全部改为从任务卡读取或在线自适应）：
- 指向偏差的搜索网格只有 ±0.16°：出现未命中后，再在 ±max(0.5°, 1.5 格) 内做粗网格拟合，并把精细网格移到最佳位置（`off_wide`）。
- 故障次数假设只到 4 次，报满后不再报告：扩展到 1–8 次，多出的次数只给很小的先验质量（`fault_counts*`）。
- 不读误报罚分：付费误报的次数上限和所需证据长度按 |false_penalty| / 150 缩放（`rep_cost_scale`）。
- 可达最高分默认 DARK 档倍率最高：改为三档最大值。
- 试过把均匀度项的边际收益加进价值（`unif_bonus`），在均匀度权重 ×100 的卡上反而净亏：只看"赛季现在结束"的梯度，会把观测拉向本来晚些时候才适合观测的赤经条带。未采用。

确认稳健、无需修改的：天气事件 ×3、天气噪声加大、火箭 ×5 加高地形、预算只给 200 秒、请求奖励 ×10、最低高度 55°（漏选的必选目标全部是 55° 以上不可见的）、曝光下限 1200 秒、完全没有事件（无误报）、20 万目标的星表（内存 1.0 GB）、赛季在 1997 年。

## 2d. 第二轮对抗自检（c22–c25）

我们继续扮演出题方：只用引擎校验允许的参数，构造极端卡、组合卡和"历史天文事件"彩蛋卡（`lab/gen_adv.py`、`lab/adv2/battery.py`）。

**最严重的发现：1970 年以前的赛季。** 引擎接受 1000 年以后的任何年份。1970 年以前的时间戳为负，而"站点关闭至"的初始值是 −1，于是智能体一直等待：c21c 在 1054 年测试卡上 0 次观测，得 −75200。c22 起改为 −1e18，并统一输出 4 位年份。

| 场景 | c21c | c25 |
|---|---:|---:|
| 1054 天关客星（开封）/ 1572 第谷超新星 / 1859 卡林顿事件 | −75200 ×3 | 27818 / 35002 / 26517 |
| 1883 喀拉喀托 / 1908 通古斯 / 1816 无夏之年 / 1960 智利大地震 | −75200 ×4 | 18712 / 13721 / 17279 / 32372 |
| 指向偏差 1.4° / 2.4° / 3.6°（规则上限 5.7°） | −15704 / 5856 / −125200 | 26625 / 29056 / 47934 |
| 地形高达 75° | −69210 | −10575 |
| 极端组合（5–12 种极端同时出现）×6 | 6005 … −75200 | 19190 … 50414 |

对应的修复：
- 全范围指向偏差搜索：一次短曝光里，不同光纤组检验不同的偏差假设。
- 地形高度在线学习：任意高度都可以，只有公告方向以外的探测也为零时才判定站点关闭。
- 事件和天气参数失配时防误报：放宽并学习事件效果先验、方向性事件期间不累积故障证据、学习地震恢复时间、天气噪声自适应。
- "最多连续上报 1 次"的精确处理。
- 请求：已开始的请求坚持完成，高奖励请求可以多投入时间，当夜即将落下的请求目标优先（c26 的 `rq_urg_intra`，7 张请求密集卡合计 +5387）。

确认引擎本身就会拒绝、因此不可能出现的配置：南极点站点、24 小时全黑的极夜、1000 年以前的赛季。昆仑站长夜（16 小时）、北纬 80° 极夜、2061 年、3001 年、9998 年的赛季都正常完成。1054 年客星在 7 月离太阳只有约 18°，暗夜里最高仰角不到 16°，这个请求在物理上就不可完成。

## 2e. 新正式赛卡 A1–D1 与实际时间上限（c27）

10 月 6 日正式赛新增 A1–D1 四张卡（"更贴近真实观测站"，不计入隐藏卡排名）。卡文件不公开，我们从自己运行的下载结果分析：
- 每卡 51–69 个观测请求，其中 40–59 个零奖励（v4 规定不能有未完成罚分），另有几个 300–500 分的请求；
- 天气事件更多，故障 3–6 次。

**问题**：引擎每一步（包括 wait-until 展开的每一段）都把所有已发布的请求与全部观测记录逐一核对，单步耗时约为 1.1×10⁻⁷ 秒 × 请求数 × 记录数。A–D 只有 6 个请求，单步 0.04–0.06 秒；A1–D1 赛季后段单步 0.2–0.4 秒，整局可能超过 1800 秒实际时间上限而被截断。c25 在 B1 上只跑完 89% 的赛季，漏选 61 个必选目标，排第 5；第一名 42686 跑完了全季。D1 几乎所有队都被截断。

**c27 的做法**：
- 在线拟合引擎在两次决策之间的时间：固定开销 + 系数 × 核对量。
- 按自身记录数和观测次数的凹增长（局部指数拟合）外推剩余赛季的引擎时间。
- 预计超出可用时间的 70% 时，逐级提高最短曝光时长（300–3600 秒），关闭期间一次等待多个时隙；关闭期间的探测曝光只用 4 根光纤。
- 已见请求不足 12 个时完全不启用，A–D 类卡行为与 c26 相同。

| 类 A1–D1 本地卡（1800 秒上限） | c26 | c27 |
|---|---:|---:|
| B 类（60 个请求） | 39295（截断） | 46077（跑完） |
| B 类（92 个请求） | 31909（截断） | 36673（跑完） |
| D 类（71 个请求） | 35087（截断） | 35382（仍截断） |
| C 类，长时间未公告关闭 | 28961 | 28896 |

平台同款 runner 的 docker 测试：类 B1 卡在 1730 秒内跑完全季。

## 4. 计时规则与"外部算力"分析

- 计费（`challenge/fair_clock.py`，规则 §5.10）：
  - 每回合计入 min(容器内全部线程的 CPU, 回合墙钟) / speed_factor，回合之间的引擎时间不计费。
  - 每张卡另有 1800 秒实际时间上限，从第一条 decision_request 起算。
- 规则 §4.2–4.3 允许外部算力和自有服务器（经平台 sidecar 访问公网 443/80 端口），等待网络的时间不计入预算。
- **结论：我们不使用外部算力，因为没有收益。**
  - c17w5 线上只用了 900 秒预算的 18–48%（B 368、A 252、C 436、D 165 秒），实际耗时 480–640 秒。
  - 搜索规模再加大（600/24/24/50k）也不再提分。
  - 外部服务还会给隐藏决赛引入网络依赖；主办方核验期间也要求服务一直可用。
- 不使用多线程（规则文字计全部线程 CPU，实现按墙钟封顶，存在灰区），也不在回合之间预先计算。预算本来就有富余，不需要这类做法。

## 5. 本地评测方法

- `lab/harness.py`：进程内运行官方 v4 引擎（`hackathon-survey26/challenge`）。
  - 每步计费 min(进程 CPU, 墙钟) × CF，并向智能体注入 speed_factor = 1/CF。CF 0.65 约等于平台中位速度。
  - `HARNESS_WALL_CAP` 可模拟实际时间上限。
- `lab/qrun3.py`：作业队列，按整机并发上限调度。两台机器：开发机 EPYC 7F72（24 核/48 线程），PRO6000 机器（i7-14700K，28 线程）。
  本机并发不超过物理核数，否则 CPU 计时膨胀，会扭曲预算行为。
- 测试世界（均用官方生成器生成）：

  | 系列 | 生成方式 | 用途 |
  |---|---|---|
  | FA/FB/FC/FD | `gen_formal_like.py`：官方公开的 A–D 卡文件 + 合成天气、事件和请求 | 线上卡的近似 |
  | FM | 同 D 卡星表，配线上 D 卡的压力配置（3 个故障，数据丢失 0.15） | 多故障 |
  | HE/HF/HG/HH | `gen_hidden_like*.py`：A–D 的仪器、站点和计分配置，新的星表、季节和天气（规格在 `lab/hspec`） | 隐藏卡模拟 |
  | X1–X7 | `gen_weird.py`：异常站点、光纤缝隙、曝光范围、季节长度、压力 | 健壮性 |
  | W001–W016 | `genworld.py`：短季合成卡 | 健壮性 |

- `lab/dockertest2.sh`：用平台官方本地 runner 在 `--cpus 2` 的 python:3.12-slim 容器中运行 ZIP，包含真实的 FairClock。
- 分析工具（`lab/tools`）：
  - `tab.py`：跨世界成绩表。
  - `reqfeas.py`：用真实天气估计必选目标的可行性上界。
  - `lossdec.py` / `gainsplit.py`：损失分解。
