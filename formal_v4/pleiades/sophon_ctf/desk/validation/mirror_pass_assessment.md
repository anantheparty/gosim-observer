# 镜子与酒吧 pass：离线结论

依据 `desk_calls.jsonl` 第1–253行、`sophon_flags.log`、房间缓存及公开 SQL/Vue；没有平台调用或提交。当前已盖章20/22，仅缺4、17。

## 镜子：题意对应原四词，优先怀疑格式或历史状态

**语义上最有依据的答案仍是 MIRROR / TOPIARY / ELEVATOR / BASEMENT。** 日志119是唯一四词门请求，且成功。题目明确限定“the four words”，没有文字依据继续改成电影名、房号或新的门。

| 事实 | 日志位置 |
|---|---|
| 首次读镜子，问题“Which door did you try first? (the four words)” | 50，19:19:09 |
| 唯一四词门 GET，路径为大写原序连字符，成功 | 119，19:50:46 |
| No.3 提交成功 | 120，19:50:54 |
| 大写原序连字符被拒 | 121，19:50:56 |
| 大写原序空格被拒 | 143 |
| 整串大写字符反转被拒 | 211 |
| THE SHINING 被拒 | 230 |

最高价值的**一个**未试字符串是：

```text
mirror-topiary-elevator-basement
```

它只改变大小写，保留唯一成功请求的四词、顺序和分隔符。可能的实现解释是开门时规范化并存入小写历史，镜子却直接比较输入。但私有代码未公开；这只是单因素、最少新假设的诊断候选，**不是已推出的正确答案**。若未来仍被拒，更合理的是审查状态合同，而非继续穷举反转和分隔符。

另外两个解释均有未验证的实现假设：

1. **历史记录时机。** 首次 GET 镜子比开门早约31分钟。若首次进入镜子时缓存了空历史，或只在错门分支记 `first_door`，或盖章清理了门历史，就可能拒绝真实成功门。现有记录不能区分这些情况；尤其不能因此故意走错门来“补历史”。
2. **身份作用域。** 可见 `/desk` 始终是 debug，found 持续增长，反对换榜或整体重置解释。公开表按 `(board, team_id, no)` 计分，却没有公开镜子个人历史的作用域；若两次请求用不同用户，仍可能成绩相同而个人历史不同。日志未记录身份和请求头，因此不能完全排除；它的优先级低于大小写。

“It only asks about you”更自然地指向请求者自己的尝试记录，不足以要求反写文字。REDRUM 已是独立 No.6；借它继续为镜子答案添加反转步骤的证据更弱。

## Pass：No.4 的实质候选，真假与副作用必须分开

第25行平台原文说在 room214 签发，可在前台交并跳过余下房子；字段为 `pass`，值为 `SOPHON{SW3A4SPNWKQ4DQ9UVS34}`。本轮未提交。

| 支持真实奖励的证据 | 限制或反证 |
|---|---|
| 串直接来自平台响应，并非猜词 | 平台也完全可以生成外形相同的诱饵串；没有公开签名验证器 |
| 未解No.4紧邻酒吧门No.3，且在打字稿No.5之前 | 编号只能支持定位，不能证明pass就是No.4；22可先于其他支线盖章，编号也不是严格前置顺序 |
| 已知真No.10在最深房被称为“a pass on the bottom step” | 只能证明“pass”一词不是伪旗判据，不能将真伪传递到酒吧这张 |
| 酒吧仍有尚未使用的独立pass字段，镜子较自然对应No.17 | 剩余编号和未用线索凑成一一对应，仍只是推断 |

room214的描述是未拆的行李箱。它**没有直接证伪**“曾在那里签过字”；“214属于不可信证词的担保房间”也不是服务端验旗证据。酒吧大量说法自相矛盾、承诺跳过整个房子、单独使用pass而非flag字段，都足以保留诱饵可能，但不能判死。

我的结论是：**pass是目前No.4最有依据的候选，比新猜词或新猜路由强；真奖励、假通行证、带剧情副作用的真实奖励三种可能都没有被排除。** “可提交的真实平台产物”与“保证有效且无风险”不是同一个结论。

## 交错会不会让 Johnny 遗忘？

- 唯一明确警告写在 `door` 字段，并紧接 `GET /desk/door/WORD1-WORD2-WORD3-WORD4`：`A wrong door and Johnny forgets everything.` 它明确覆盖错门，**不能直接推广为所有错误flag都会重置**。
- 过去普通猜测走 `/desk/flag` 返回422。比如18:59:47的zampano发生在No.1、No.2成功后；后续酒吧仍可访问，最新found保留原解题时间。没有观察到这种普通wrong_answer清空进度。
- **酒吧pass可能被专门识别并走特殊分支。** 普通错误flag的行为不能替它担保安全；“签发形状相同”同样不能担保。
- Vue `SophonBoards.vue:51` 只是将trim后的flag交给私有函数，没有客户端reset；迁移SQL把已解旗和完赛记录放在独立表。两者有助于区分“剧情状态遗忘”和“已盖章分数删除”，但私有函数仍能有服务器端副作用。不能据此保证20个成绩永不被删。
- `/desk` 的 `pending=[]` 也不足以判断pass真假：现有记录缺少可靠的“已签发但尚未提交的真flag”正对照，pending字段的含义未公开。

因此，**没有证据证明提交pass必然触发遗忘，也没有依据保证它绝不触发。** 若主线要在余下动作中选一次实验，我倾向于优先评估这张真实平台产物；但是否接受特殊剧情重置的未知风险，仍由主线决定。本轮只给判断，没有调用hand_in或任何答题接口。
