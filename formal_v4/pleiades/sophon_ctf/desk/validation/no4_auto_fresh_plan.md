# No.4：用独立 auto 状态验证假 pass 的时序

**冻结说明（2026-10-07）：此文仅保留历史实验设计，不是运行授权。所有 Sophon 新运行包
已暂停；不得上传或运行候选包。下述独立剧情状态必须另行验证，SQL 的独立计分不能证明它。**

当前 debug 状态不能回答“假 pass 是否必须立即提交”：酒吧在第 5 次 POST 首次且唯一返回
`pass`，但当时没有提交；实际提交发生在 9 小时 28 分钟后，服务端返回 `fooled`。根页在
pass 出现后、正确四词门前仍没有 No.4，现有日志也没有重置这段状态的安全合同。

若未来运行内认证被真实响应和榜单证明为 `board=auto`，SQL 只能证明成绩按
`(board, team_id, no)` 独立计数。还需确认剧情状态、酒吧计数和 pass 领取历史也独立，并取得
新的运行授权，才可能做以下受控对照：

1. 只调用已知正确的基础入口 `POST /desk/door {"say":"THE SHINING"}`；不访问任何
   `/desk/door/*` 子路由，也不猜门。
2. 有界调用酒吧（最多 12 次，无重试循环），直到响应中出现格式正确的 `pass`；pass 只保留
   在内存，不写盘、不打印。
3. 在同一个请求流程里立刻向 auto 的 `/desk/flag` 提交该原串，记录状态、固定错误枚举、
   `board/solved/no`，以及响应若实际签发 `SOPHON{...}` 时的签发码。
4. 任一步身份不明、board 不是 auto、429、超时或响应结构异常，立即停止；不回退到 debug，
   不切换认证模式。

若立即提交实际取得 No.4，才能确认该对照成功；若仍被判假，只能排除“立刻处理足以领奖”，
不能证明 No.4 与 pass 无关。未确认剧情隔离前，也不能承诺它不改变 debug 状态。
批量重交已知旗标是另一项动作，继续保持禁用，等待用户对该项的单独决定。
