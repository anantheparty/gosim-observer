# Johnny 第一封邮件：离线推导与榜单可见性

本轮仅读取用户指定会话 JSONL 的第 14151 行，以及公开仓库源码。没有联网、没有调用提交脚本。
下面的 5 个字符串都只是候选，**没有任何一个已被证明能通过服务端**。

## 先修正一个判断

422 的原始 JSON 是 `error=wrong_answer`、`johnny=That doesn't look like anything from here.`。
这表明服务器将这些输入判为错误答案，不能据此断定“必须是平台动态签发/带签名的串”，
也不能断定只是格式错误。缺少私有实现时，仍可能是静态答案、分关答案、运行回执或混合机制。
前端只读取 `body.message`，而本次错误解释在 `body.johnny`；两者存在字段差异，
所以判断应以保留的原始响应为准，而不是页面显示是否为空。

## 邮件可以确定推出什么

所有矩阵均非简并，分成两组共同本征基：`{Z,D,E}` 与 `{X,R,S}`。
对本题限定的这两组，等式对所有 a′、c′ 成立，当且仅当 A 与 B 同基，或 B 与 C 同基。
若 A、C 同基而都与 B 不同基，左边为 1/2，右边为 0 或 1，不能恒等。
这只是本题矩阵集合的判据，不推广为任意三种可观测量的必要条件。

| 行 | 三元组 | 成立 | 8 位编号所交换的位置 |
|---:|---|---|---|
| 1 | Z,X,D | 否 | 1↔6 |
| 2 | Z,D,X | 是 | 6↔7 |
| 3 | X,D,E | 是 | 3↔7 |
| 4 | R,E,S | 否 | 4↔5 |
| 5 | Z,D,E | 是 | 1↔4 |
| 6 | R,S,Z | 是 | 5↔8 |
| 7 | D,S,E | 否 | 7↔8 |
| 8 | S,Z,R | 否 | 2↔5 |
| 9 | D,R,X | 是 | 3↔5 |
| 10 | E,Z,R | 是 | 1↔2 |
| 11 | E,R,Z | 否 | 3↔8 |
| 12 | Z,S,R | 是 | 1↔3 |

独立用 2×2 矩阵本征向量数值核对，恰为有效行 2、3、5、6、9、10、12。
112 字符密文分成 14 个 8 字符块，逐块按有效行从上到下交换，恰得已有明文。
取位定义为 `out[k]=in[p[k]-1]` 时，解密置换是 `84216735`；
其逆置换 `43728561` 将整段明文准确还原密文。后者是逆映射，不是前者字符串倒序。

因此数学选择、分块、顺序、置换方向均有完整的正反验证，当前没有理由认为第一层解密错了。
可复核的逐行数据与往返结果：`validation/johnny_first_mail_derivation.json`。

## 哪些信息已使用，哪些仍未解释

| 信息 | 目前解释 | 是否支持再抽一层 |
|---|---|---|
| 12 个三元组的字母 | X/Z 定义两种不相容基；D/E、R/S 制造同基但不是同一个符号的情形，供筛选有效行。 | 字母已有数学用途。直接取有效/无效行的三列，均没有得到可读文本；不能擅自加映射表。 |
| 5 个干扰项 | 全是 A、C 同基而 B 异基的反例，作用是排除它们的交换。 | 不是“尚未使用的五条密钥”。只作用干扰项或作用全部 12 项均不产生对应明文。 |
| 编号本身 | 每个都是 1–8 的单次对换；7 次有效交换构成完整解密置换。 | 已充分使用。逆映射仍是一个精确、未提交过的候选，但题面没有说最终答案要交置换。 |
| top to bottom | 固定交换顺序；这些交换不全可交换。反序不能解出那句明文。 | 明确用于解密，暂无第二种必要解释。 |
| Mary | 信件收件人；没有给出 Mary 的姓、索引规则或她与小说的具体关系。 | `DEARMARY` 确为 8 字符，但用正/逆置换只得 `YREDARAM` / `RAREYMAD`，未见额外意义。无法据此可靠跳到 Mary Shelley 等人物。 |
| Johnny + 借来的小说 | 明文“叶子的集合/无尽的房子”指向 House of Leaves；Johnny 可进一步关联 Johnny Truant。 | 有语义证据，但不能确定题目要求书名、角色名，还是后续动作。 |
| JAN 5 1997 | 上轮已查到作者网站读者年表把此日列为 Zampanò 留给手稿发现者/出版者的注记日期。 | 强化 House of Leaves / Zampanò 关联；不是一个自然唯一的 flag 编码规则。 |
| final trials / after | 明文给的是叙事/后续提示，没有“flag is …”或提交格式指令。 | 可能暗示后续关卡或最终验收，不能认定首封邮件本身一定结束一个签到关。 |
| 小写连字符 | 练习码展示了这种命名风格，且以前主要试了大写无分隔书名。 | 可支持一次规范化假设；练习码明确不可提交，不能推出所有真 flag 必须同形。 |

角色与日期使用上一轮已经核对的资料，本轮未做新网络查询：
[出版社导读](https://www.penguinrandomhouse.com/books/36526/house-of-leaves-by-mark-z-danielewski/9780375703768/readers-guide?pubDate=20260610)、

## 至多 5 个候选，按相对把握排序

排序只表示现有证据的强弱；没有高把握候选，不建议为了凑次数全交。

| 排序 | 候选 | 推理与局限 |
|---:|---|---|
| 1 | `SOPHON{house-of-leaves}` | 明文最明确指向的小说书名，采用已见的小写连字符风格。与已拒绝的 HOUSEOFLEAVES 不同。语义有依据，准确格式仍是假设。 |
| 2 | `SOPHON{43728561}` | 这是经往返验证的**加密**取位置换，区别于已拒绝的解密置换 84216735；若旧 key 指加密密钥，这个方向合理。没有证据说 desk 要收数值密钥，故仍偏低把握。 |
| 3 | `SOPHON{johnny-truant}` | Johnny 签名加上 House of Leaves 指向书中整理手稿的 Johnny Truant。需要额外假设“要交人物全名”，邮件未明确要求。 |
| 4 | `SOPHON{zampano}` | JAN 5 1997 对应手稿注记，可能要找注记作者；用无重音拼写。人物关联有旁证，但选择人物及拼写规范均未获官方确认。 |
| 5 | `SOPHON{the-shining}` | 真卡反复拼出 THESHINING，尝试同一书名/片名的小写连字符形式。它属于天空线索，不是首封邮件直接推出的结果，故排最后。 |

没有列 `johnny-homework-ok` 等自行发明的后缀，也没有列随机哈希、日期排列、三元组字母重编码。
题面不提供这些转换规则，增加候选只会变成盲猜。

## 旧 key 与新 desk flag：能确定的关系很有限

旧 `private.sophon_solves` 以 team_id 为主键，必须有 run_id，另存 user_id、solved_at、key 文本。
公开 `sophon_solvers()` 只返回队名/时间，不返回 key。数据库没有规定 key 的文本格式，
它可以是答案、密钥标识或服务端记录；不能仅凭列名认定等于新 `SOPHON{...}` 的花括号内容。

新 `private.sophon_g_solves` 以 `(board,team_id,no)` 为主键，支持多关及 debug/auto，run_id/user_id 可空。
公开仓库没有从旧表复制到新表的 SQL/trigger，也没有 desk/flag 的私有校验实现。
所以旧谜题进度、新榜进度可能并存；两者是否兼容或如何对应，当前无法推出。
即使新榜全空，也仍可通过既有只读 `sophon_solvers()` 检查旧版是否有可见记录。

## 三榜为空的准确含义

对普通调用者，每条记录须满足：

```text
记录所属队伍不是 hidden
且 current_competition() 在该调用身份下包含 extra_phase_id 键
```

第二项取决于**读取者身份**，不是记录所属队伍身份；admins 走另一个可见分支。
extra_phase_id 仅在阶段启用、projects_enabled、处于开放时间段、且调用者满足 access_team_id 限制时出现。
`tests/test_current_competition.py` 已明确测试：受限阶段中，匿名 solvers 返回空，允许的队员能看到名单。
新 `sophon_g_visible` 使用相同开放条件。

| 同一查询身份下的情况 | 空结果能说明什么 |
|---|---|
| current_competition 缺 extra_phase_id | 普通用户的三个新榜都被过滤；不能判断有人解出与否。 |
| 包含 extra_phase_id，RPC 成功返回 `[]` | 新表没有该身份可见的记录；仍不能排除隐藏队、旧表记录或尚未结算的解题。 |
| 仅 finishers 为空 | 只说明无可见完赛者，不能说明无人完成部分关卡。 |
| 只有网页空表，未检查 RPC error | Vue 会把请求失败也替换成 `[]`，连“成功查到零条”都不能确定。 |

因此当前最稳妥表述是：**“这次调用没有返回可见的新榜解题记录。”**
普通用户若能在新鲜页面看到 Sophon 入口/用 `--phase extra` 开评测，是 gate 开放的旁证，
但不能证明另一次**匿名**榜单请求也通过 gate；还要排除缓存及身份不同。

建议主会话只读保存同一身份、相近时刻的 `current_competition()` 原始 JSON 与三榜 HTTP 状态/响应，
再读一次旧 `sophon_solvers()`。有了这些，才能区分“可见性挡住”和“新表确实暂无可见记录”。
